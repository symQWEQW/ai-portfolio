# RAG 召回调优：从指标到实验（v2 重写）

> 基于某地 AI 预审项目的真实实验数据。本文所有数字来自仓库 [`RESULTS.md`](https://github.com/symQWEQW/preaudit-rag-engine/blob/master/RESULTS.md)（v2 评估重建），由 `run_eval.py` 现场跑出。
>
> **版本说明**：本文早期版本曾引用「500 字切片 Recall@5 = 1.000」、以及后来重建版的一组读数作为结论，两组数字均已**撤回**。前者是评测口径上的算术必然，后者对语料排版敏感、不可复现。本版按「元数据不参与切分」的确定性构建方式重写。

## 1. 先撤回两个「好看数字」

旧评测：5 篇模拟政策文档、合计 1,473 字，15 道题。500 字切片时每篇文档刚好切成 1 个 chunk，**整个库只有 5 个 chunk**，而计分窗口是 `top-5`：

```
top-5 ⊇ 全部 5 个 chunk
⇒ 对任意问题，top-5 ∩ gold 是否为空只取决于 gold 是否非空
⇒ 15 题 gold 全非空 ⇒ HitRate@5 恒等于 1.000，与检索质量无关
```

`Recall@5 = 1.000` 同理（top-5 包含全部 chunk，自然包含全部 gold）。

**发现并撤回了被语料规模撑起来的满分读数** —— 这一步比多贴一个好看数字值钱。但重建后的第一版仍把 `SOURCE:` / `POLICY:` 溯源行放在被切分的正文里，它们一改长度，500 字定长切片的边界就整体漂移，指标跟着变（同一套代码随排版不同会跑出多组互相矛盾的读数）。**于是又把那一组撤回**：它不是模型能力，是排版巧合。

最终版把溯源元数据从切分正文中剥离、改存 `data/sources.json`，chunker 只看政策正文，指标才确定下来（连续两次运行、重建语料后再运行，输出逐字节一致）：

| | v1（旧，已作废） | v2（现行，确定性） |
|---|---|---|
| 语料 | 5 篇 / 1,473 字 | **16 篇 / 12,299 字 + 4 篇干扰 / 479 字** |
| 题库 | 15 题（gold 指文档） | **38 题**（gold 精确到文档，附原文依据） |
| k | 单一 k=10 检索、按 k=5 计分 | **k = 3 / 5 / 10 三档** |
| HitRate@5（500 字） | ~~1.000~~ | **0.921** |
| Recall@5（500 字） | ~~1.000~~ | **0.490** |
| MRR@5（500 字） | 0.967 | **0.639** |

加 4 篇干扰文档是刻意设计：无干扰时 12 篇 / 30 chunk，k=10 就占 1/3 库；加干扰后 20 篇 / 36 chunk，top-k 才有区分度。

## 2. 切片粒度不是越大越好，也不是越小越好

500 字切片（**36 chunk**）、仅向量检索（TF-IDF）：

| 指标 | k=3 | k=5 | k=10 |
|---|---|---|---|
| HitRate | 0.816 | **0.921** | 1.000 |
| Recall | 0.384 | **0.490** | 0.714 |
| MRR | 0.614 | **0.639** | 0.651 |
| Precision | 0.368 | 0.284 | 0.216 |

三档切片在 k=5 的对比：

| 切片 | chunk 数 | HitRate@5 | Recall@5 | MRR@5 |
|---|---|---|---|---|
| 200 字 | 76 | 0.947 | 0.237 | 0.625 |
| 300 字 | 52 | 0.921 | 0.373 | 0.621 |
| **500 字** | **36** | **0.921** | **0.490** | **0.639** |

**结论**：切片越小 HitRate 越高（更容易「碰到」相关文档），但 Recall 和 MRR 显著下降——知识点被切碎，同一问题的相关片段散落在多个 chunk 里，命中一个不等于召回齐全。**500 字在 Recall / MRR 上最优，200 字 HitRate 略高但 Recall 只有 0.237**，综合判断 500 字最优。生产建议：按语义单元切片 + 句边界 + overlap，别只调字数。

## 3. 重排序（rerank）的价值在双阶段架构，但这次没证明出来

理想形态：

```
第一层：向量语义召回（embedding / Milvus）—— 对近义表述敏感，易召回噪声
第二层：cross-encoder 精排（bge-reranker-v2-m3）—— 按「查询-片段」真实相关性重排
```

而本项目当前实现是 **TF-IDF 召回 + BM25 精排，两者同源**（都是词频模型）。实测：

- **只有小切片上 MRR 小幅提升**：200 字切片 MRR@5 从 0.625 → 0.651（+2.6 点）；300 字 0.621 → 0.657（+3.6 点）。
- **500 字切片反而全部下降**：HitRate@5 0.921 → 0.895，Recall@5 0.490 → 0.469，MRR@5 0.639 → 0.615。
- 根因：BM25 原始分 3.5–8.8 与余弦分 0.09–0.28 量纲差约 30 倍，alpha 从 0.0 扫到 0.9 排序几乎不变。

**这不是缺陷披露，是结论**：同源精排不可能带来数量级提升。它只能证明「重排不会显著变差」（某些切片下甚至变差），证明不了「重排有效」。要释放 rerank 的价值，得把第一阶段换成 `bge-small-zh-v1.5` + faiss 语义召回、第二阶段换 cross-encoder —— 这是报告里写明的下一步，而不是含糊带过「rerank 通常提升 5%–15%」。

## 4. 未命中分析比平均分更有信息量

38 题中有 **3 题**在 HitRate@5 未命中（500 字切片，HitRate@5 = 0.921）：

| 题号 | 问题 | gold | 实际 top1 | 原因 |
|---|---|---|---|---|
| `D03` | 糖尿病眼底病变要达到什么分期？ | `糖尿病__02_认定条件组合` | `糖尿病__03_认定注意事项` | 概括性文档（「须提供并发症佐证」）盖过具体分期条款 |
| `D06` | 糖尿病 ASCVD 合并心功能不全需要满足哪些条件？ | `糖尿病__02_认定条件组合` | 干扰文档（慢性肾功能不全） | 「肾病」「心功能」词面重叠把正确条款挤下去 |
| `C01` | 恶性肿瘤的首选确诊依据是什么？ | `恶性肿瘤__02_认定条件组合` | `恶性肿瘤__04_申报条件与材料目录` | 两篇都提到「病理」，申报条件篇词频更集中 |

**这三条都是有意义的失败**：前两条说明「概括性文档 / 干扰文档抢夺细节条款排名」是真实难点，解法是标题 / 条款号加权或二级精排，不是加数据。`D06` 被干扰文档抢走，恰好证明**干扰集确实起了作用**——没有干扰时这题能过。

## 5. 量化评估是 AI 工程师的标配

不靠「感觉 RAG 变好了」：固定题库、每次改动（切片、top-k、rerank）都出一组对比数字，并显式处理边界。`rag_core/eval.py` 重写四个指标，`tests_eval.py` 覆盖 **20 项断言全部通过**（空 gold / k≤0 / k 大于候选数 / 空候选 / 单文档多 chunk 展开为 chunk 级集合）。

复现：

```bash
cd preaudit-rag-engine
python build_corpus.py    # 从真实 xlsx / html 重建语料
python run_eval.py        # 三档 k × 三档切片，写 data/eval_result_v2.json
python tests_eval.py      # 20 项边界断言
```

完整报告、逐题明细与旧结论撤回清单见仓库 [`RESULTS.md`](https://github.com/symQWEQW/preaudit-rag-engine/blob/master/RESULTS.md)。
