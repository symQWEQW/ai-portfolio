★ 最想让面试官看到的一件事

发现并撤回了被语料规模撑起来的满分读数。

旧评测里「HitRate@5 = 1.000 / Recall@5 = 1.000」不是模型好，而是 5 篇语料切成 5 个 chunk、计分窗口恰好也是 top-5 —— top-5 ⊇ 全部候选，满分在数学上必然。重建为 16 篇 / 13,390 字 + 4 篇干扰、38 题、k=3/5/10 三档后，真实读数是 HitRate@5 0.974 / Recall@5 0.549 / MRR@5 0.715。愿意把自己的漂亮数字作废，比多贴一个好看数字值钱。

  • 职责解耦：病种识别 / 政策检索 / 合规审核可独立优化与替换，Retriever 可换成上面的 RAG 服务。
  • 可观测：每个 Agent 的输入输出单独记录、评估、重试，比单条提示词链更好定位问题。
  • 可扩展：后续加申诉 Agent、人工复核 Agent 复用同一张图。
  • 取舍：比 Dify 拖拽更可控，代价是要自己维护图状态与失败重试；适合规则多、需审计的政务合规场景。
当前边界（如实写）：这是本地回环的编排演示，Agent 逻辑为 mock，尚未接入真实 LLM 与政策库，也没有上线、没有接入生产预审链路。价值在架构设计与可替换性，不在业务闭环。

局限必须一起说：26 条属于极小样本演示，F1 绝对值 0.150 仍然偏低 —— 模型学到的是领域话术与结论倾向，远未达到可上线水平（真实项目建议 200–1000 条垂直语料 + 7B 基座）。这个项目的价值是完整跑通「训练 → 评估 → 用指标证明提升」的工程闭环，不是追求 SOTA 分数。
踩过的坑也写进 README 了：Instruct 模型训练 / 推理必须套同一套官方 chat 模板（裸 prompt 下 Base bigram-F1 仅 0.038）；CPU 上别用默认 bfloat16（软件模拟单步 73 秒 → float32 后 0.5 秒）；推理必须传 eos_token_id 否则无限续写稀释 F1。
